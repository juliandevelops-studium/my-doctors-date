# Decisions

Binding design decisions of Group 14. A decision changes only by a PR that edits this file first. Sources: `notes/1_Structure.md`, `notes/User_Flows.md`, `notes/Löschkonzept.md`, `notes/README.md`.

## Decisions from the planning phase

| # | Point | Decision | Reason |
|-|-|-|-|
| 1 | Ingress and service authentication | Traefik (shipped with k3d) + signed service tokens + NetworkPolicy. No ingress-nginx, no mTLS. | k3d brings Traefik and NetworkPolicy enforcement; mTLS needs certificate management in the cluster. Deviation to be reflected in the documentation. |
| 2 | Booking confirmation | Auto-accept (UF-05). New bookings get `bestaetigt`. The status `angefragt` stays in the schema for a later approval flow. | Less reception work, fewer states to secure. |
| 3 | Roles vs. groups | No groups. A person can have several roles (`user_roles`). "Nutzer" is implicit for every account. | Simplest model that fulfils the matrix. |
| 4 | Retention periods A to E | Defaults from the Löschkonzept, stored in `config`, changeable by the system admin. C must stay >= B. | Löschkonzept says they are configurable. |
| 5 | "Eigene Nutzerdaten" in the matrix | Applies to every authenticated user, because every role is also a Nutzer. | Matrix column "Nutzer" is the base role. |
| 6 | Cancellation deadline | None. Only appointments in the past cannot be cancelled. | UF-07 leaves the deadline open; no deadline keeps the rules testable. |
| 7 | Track owners | **Open.** Needed to fill `.github/CODEOWNERS`. | Team decision. |

## Decisions made while writing the contracts

| # | Point | Decision | Reason |
|-|-|-|-|
| 8 | OpenAPI version | OpenAPI **3.0.3**, not 3.1. | `oapi-codegen` (v2.5) does not support 3.1 (`type: [string, "null"]` fails). 3.0.3 keeps `make gen` working. Deviation from the implementation plan. |
| 9 | `systemadmin` is an exclusive role (confirmed) | A user with `systemadmin` cannot hold any other role. Role assignment returns `422` otherwise. | The matrix denies the system admin access to appointment data. A combined admin + reception account would circumvent that (separation of duties). |
| 10 | Token transport | `user_service` returns the JWT in the JSON body. `frontend_provider` stores it in the HttpOnly cookie and sends it to the backend as `Authorization: Bearer`. The browser never talks to a backend service. | Matches the architecture diagram and SR.03 (identity only from the validated token). |
| 11 | Login is two-step, MFA is mandatory | `POST /auth/login` returns a short-lived MFA challenge (5 min) after a correct password. `POST /auth/login/mfa` exchanges challenge + TOTP/recovery code for the access token. A user without confirmed MFA (new account, bootstrap admin, UF-03) gets a token with `scope=setup`. It is accepted only by the routes marked `scope: setup` in `api/authz.yaml` (change password, MFA setup, logout, own profile). | UF-02 requires MFA; UF-03 requires that nothing else is reachable before password change and MFA setup. |
| 12 | Token lifetime and revocation | Access token 15 min, no refresh token (user logs in again). Each token carries a `jti`. Every service checks `jti`, `sub` and `iat` through the middleware operation `tokenCheck` (revoked `jti`, `users.sessions_valid_after`, account status). Role changes, password changes, resets and account deletion set `sessions_valid_after`. | UF-12 requires that all sessions become invalid after a reset. Needs the new column from migration `0008`. |
| 13 | Roles inside the token | The token carries `roles`. A role change takes effect immediately because it also sets `sessions_valid_after` (decision 12). | Avoids a database lookup of roles on every request, without stale rights. |
| 14 | Mail templates | `mail_service` accepts only a fixed set of templates with typed parameters, and each caller may use only its own templates. No free-text mail API. | Prevents a compromised service from sending arbitrary mail (phishing via the practice's sender address). |
| 15 | Patient search for reception | `GET /patients` lives in `calendar_service` (allowed: `desk`, `organisator`). | The reception needs it to book for a patient and to set the main doctor. The system admin has no access (matrix). |
| 16 | Internal routes | `database_middleware` and `mail_service` are never reachable via Ingress. They accept only service tokens. | SR.02, decision 1. |
| 17 | OpenAPI is the contract, `api/authz.yaml` is the authorisation source | `docs/authz-matrix.md` is generated from `api/authz.yaml` (`make check-contracts`). `scripts/contractcheck` fails if specs and `authz.yaml` differ. A Go test in each service later compares the registered chi routes with `authz.yaml` (SR.03 review criterion). | One place to change, mechanical consistency. |

## Decisions made while implementing

| # | Point | Decision | Reason |
|-|-|-|-|
| 18 | Practice time zone | Working hours are local time in `Europe/Berlin` (env `PRACTICE_TZ` of `database_middleware`). Timestamps in the API stay UTC. | `working_days` stores times without a date. Daylight saving time must not shift the doctor's day. |
| 19 | Contract changes after `contracts-v1` | Allowed, spec first, with the checks green. So far: the route `mfaDisable` and `409 mfa_active` on `mfaSetupStart` and `mfaSecretUpsert` (decision 22); the middleware operation `mfaUseStep` (decision 23); the mail template `email_change_notice`; named schemas for audit, doctor and window items; migration `0002_practice` seeds the service "Sonstiges". | Found while implementing. Without the seed row UF-06 could never work. Without a rule for MFA re-setup, an abandoned re-setup could leave an account without MFA. |
| 20 | Session invalidation | Password change or reset, role change, MFA removal and account deletion set `users.sessions_valid_after` to the **next full second**. `tokenCheck` rejects tokens with `iat` before it. Tokens issued by `user_service` for that account afterwards carry `iat = max(now, sessions_valid_after)` (access tokens and the MFA challenge), so they are valid at once. | JWT `iat` has whole seconds. Without the "next second" rule, a token issued in the same second as the change would survive it (found by `TestMfaDisableAndReplace`). Assumes the clocks of the pods and the database differ by less than a second (one k3d host). |
| 21 | Concurrency and overlap | The only protection against double booking is the exclusion constraint. The middleware does not check availability first. Working-hour and specialty checks belong to `calendar_service`. | A check-then-insert race is impossible this way. Verified by `TestParallelBookingsOneWins` (12 parallel requests, exactly one `201`). |
| 22 | MFA can only be replaced after removing it | `mfaSetupStart` answers `409 mfa_active` while MFA is confirmed, and the middleware never overwrites a confirmed secret (`mfaSecretUpsert` gives `409 mfa_active`). Replacing MFA means: `mfaDisable` (password + valid code or recovery code), which deletes secret and recovery codes and revokes all sessions, then login (`scope=setup`) and a new setup. No admin override. | Keeps one secret per user and no half-replaced state. A lost device is handled by a recovery code in `mfaDisable`. Accepted: the first enrolment (new account, or after `mfaDisable`) is protected by the password only, as UF-03 requires. |
| 23 | TOTP replay protection | A TOTP time step is accepted once (`mfaUseStep`, `mfa_secrets.last_step`, migration `0011`); codes of an older or the same step are refused. Window: one step before and after now. | RFC 6238 requires it. Without it a code seen over a shoulder or in a log stays usable for 90 seconds. |
| 24 | Recovery codes and TOTP secret at rest | Recovery codes are stored as HMAC-SHA-256 with a key (`MFA_KEY`), the TOTP secret as AES-256-GCM with the user id as additional data. Both use the same 32-byte key from a Kubernetes Secret. | A database dump alone is not enough to use either. The ciphertext cannot be moved to another account. |
| 25 | Rate limits (429) | Public routes 30 requests per minute and client (`X-Forwarded-For` of `frontend_provider`, the only caller), login 10 per minute and e-mail address, sensitive routes (password, e-mail, MFA, deletion) 10 per minute and user. In memory, per replica. | Complements the account lock of SR.05; the lock does not stop one client from trying many accounts. |
| 26 | Admin-created users | The administrator creates the account with a random throw-away password hash and a reset link (24 h). The administrator never sees or sets a password. The account must change the password and set up MFA at the first login (`must_change_password`). | UF-10, UF-03. |
| 27 | Optional login warning | The template `login_warning` exists, but the mail is only sent with `LOGIN_WARNINGS=true`. Default off. | UF-02 step 7 says optional; a mail per login is noise for a doctor's practice. |
| 28 | Mail content | Plain text only, German, no HTML, no tracking. Times are shown in the practice time zone. The booking reason and infos never appear. Parameters are typed and exact (`api/internal.md` section 5), and links must point to `PUBLIC_BASE_URL`. | A mail from the practice's address is trusted by patients, so a compromised service must not be able to send arbitrary text or links. |
| 29 | SMTP | `SMTP_TLS=starttls` by default, the certificate is always verified, there is no fallback to plain text, credentials only over TLS. Mailpit (demo) uses `none` and logs a warning. | Production relays need TLS; the demo needs no certificate management. |

## Booking rules (calendar_service)

| # | Point | Decision | Reason |
|-|-|-|-|
| 30 | Bookable times | Start times lie on a 15-minute grid counted from the start of each free block of a doctor. A service must fit completely inside one working window and must not overlap a busy interval. Nothing in the past is offered. A booking may start at any whole minute but must fit the same rules. | Simple, predictable for patients; reception can still book odd times. |
| 31 | Who gets the appointment | Patient with a main doctor: only that doctor, even if others offer the service (UF-05 case A). If that doctor is busy the booking fails with `slot_taken`, it does not fall back to another doctor. Patient without a main doctor: union of the matching doctors without doctor ids; on booking the **least busy doctor of that day** (ties by id) who is free gets it. A booking that loses a race moves on to the next doctor. | UF-05, Structure notes. Spreading by load keeps the doctors evenly booked. |
| 32 | "Sonstiges" | Lasts 60 minutes, has no specialty, and a patient booking gets **no doctor**; reception assigns one (UF-06). Availability for a patient is the union over all doctors, or the main doctor's times. Assigning checks the working time and, for normal services, the specialty; a busy doctor gives `409 slot_taken`. | UF-06. |
| 33 | One arbiter for overlaps | `calendar_service` checks working time and specialty, but whether a slot is free is decided only by the exclusion constraint in the database (decision 21). The list of busy times is used to offer times and to order the doctors, never as the final check. | No check-then-insert race. `TestParallelBookings`: 12 requests, one doctor gives 1 success, two doctors give 2. |
| 34 | Ownership with several roles | Reception and organisator see all bookings. Otherwise the caller may see the own bookings (role patient) and the own calendar (role doctor); a person with both gets the union. Ownership is part of the SQL query (`owner_patient_id`, `owner_doctor_id`), so a foreign booking is not found (404). For the union the first 200 entries of each source are merged. | SR.03. |
| 35 | Key set of user tokens | `calendar_service` fetches the public keys from `GET /v1/jwks` of `user_service`, refreshes at most once a minute on an unknown key id, and checks every token with `tokenCheck` (cache 10 s). | Key rotation without a restart, no request storm from forged key ids. |
| 36 | Times in answers | Every service sets `time.Local = UTC`, so answers carry UTC even on a developer machine. | `api/CONVENTIONS.md`: RFC 3339 in UTC. |

## Platform (Phase 1)

| # | Point | Decision | Reason |
|-|-|-|-|
| 37 | No pipeline yet | The GitHub Actions pipeline (SBOM, SAST, SCA, secret scan, quality gate, registry push) is not part of Phase 1 by request. `make up` builds the images from the working tree and imports them into k3d. The manifests use image names with a tag in `deploy/overlays/local`; a registry overlay would pin the same names to digests. Third-party images (PostgreSQL, Mailpit, migrate, Node, busybox) are already pinned by digest. | The cluster scripts do not depend on the pipeline, and the pipeline can be added without touching the manifests. |
| 38 | Local CA instead of mkcert | `scripts/secrets.sh` creates a CA with openssl once (`secrets/ca.*`, ignored by git) and signs the certificate of `praxis.localhost` with it. The user trusts the CA once. | No extra tool, no sudo, no change of the system trust store by the script. The tech stack allowed a self-signed or mkcert certificate. |
| 39 | Ports and host name | HTTPS 8443, HTTP 8080, host `praxis.localhost` (resolves to 127.0.0.1 on current systems). The HTTP redirect keeps the port. Override with `PRAXIS_HTTPS_PORT`, `PRAXIS_HTTP_PORT`. | No privileged ports, no `/etc/hosts` edit. |
| 40 | Database access model | Two roles: `praxis_owner` (owns the schema, runs the migrations) and `praxis_app` (select, insert, update, delete only; used by `database_middleware`). `pg_hba.conf` has only `hostssl` lines, `ssl_min_protocol_version=TLSv1.2`, the client verifies the server (`sslmode=verify-full`). The key of the internal database CA is deleted right after signing. | SR.02, "SQL über TLS", least privilege. A SQL injection in the middleware cannot change the schema. |
| 41 | NetworkPolicy model | Default deny (ingress and egress) in namespace `praxis`, DNS allowed for every pod, and one policy per workload that lists exactly the edges of the architecture diagram. No egress to the internet. Verified with test pods that carry the labels of the services. | SR.02, decision 1. |
| 42 | Pod hardening | Namespace enforces Pod Security "restricted". Every pod: non-root, read-only root file system, no privilege escalation, all capabilities dropped, seccomp RuntimeDefault, no service account token. Secret files are mounted read-only with mode 0440 and `fsGroup`. | Defence in depth next to the distroless images. |
| 43 | Secret lifecycle | `scripts/secrets.sh` creates what is missing and never replaces existing secrets. Random values exist only in Kubernetes Secrets and in the ignored `secrets/` directory (CA, note with the bootstrap administrator). Rotation is delete + `make up` + restart. | "Secrets nie im Repository"; a second `make up` must not log everybody out. |
| 44 | Mailpit UI | Not exposed by the ingress and not reachable from other pods; `make mail-ui` uses a port-forward. | The UI shows every mail including reset links. |
| 45 | Placeholder frontend (replaced by the real frontend, decisions 47 to 54) | A Node program without dependencies serves one page and `/healthz` until Phase 4. | Lets the ingress, the policies and the pod security be tested now. |
| 46 | Probes | All services answer `/healthz` without a token (no data). PostgreSQL's readiness checks TCP, because the temporary server of the initialisation only listens on the socket. `user_service` starts listening before it creates the bootstrap administrator and `database_middleware` retries its first database connection for a minute (a new pod has no network rules for a moment). | Found by the first cluster runs; otherwise a slow database or that start-up race made Kubernetes kill and restart the services. |
| 47 | Frontend without JavaScript (confirmed) | The UI is server-rendered (Express, Nunjucks) and uses no script at all. This allows `script-src` to be absent (`default-src 'none'`), removes DOM XSS as a class, and keeps the frontend free of logic. The MFA QR code is an inline SVG made on the server. Cost: no live updates, no client-side validation beyond HTML attributes. |
| 48 | Session cookie (confirmed) | The 15-minute user JWT is stored in `__Host-session` (HttpOnly, Secure, SameSite=Strict, Path=/, no Domain). No refresh token (decision 12): after expiry the user logs in again. The token is never put into a page, URL or log. |
| 49 | CSRF (confirmed) | SameSite=Strict alone is not relied on. (Origin "null", which browsers send with the no-referrer policy, counts only when Sec-Fetch-Site is same-origin.) Every POST needs the HMAC-bound `_csrf` field matching the `__Host-csrf` cookie and a same-origin `Origin` / `Sec-Fetch-Site`. Both are rotated at login and logout. Missing or wrong -> `403` before any backend call. |
| 50 | No authorisation in the frontend (confirmed) | Menu entries are hidden by role only for convenience. Every page calls the backend, which decides (SR.03). A user who types a URL for another role gets the backend's `403` / `404`, shown as a plain error page. |
| 51 | Mail links need a click (confirmed) | Links in mails open a page with a button; the POST changes state. Mail scanners and link previews that fetch the URL do not verify an address or confirm an e-mail change. |
| 52 | Setup scope (confirmed) | A `setup` token (password change, MFA not set up) can only reach `/setup`; the frontend redirects there, the backend enforces the scope. Recovery codes are shown once, on the page that follows the confirmation. |
| 53 | Error pages (confirmed) | Backend problems are mapped to short German messages by `code`; unknown problems show a generic page with a request id. The login answer is the same for unknown user, wrong password and locked account. |
| 54 | End-to-end test in the repository (confirmed) | `make e2e` drives the real stack through HTTPS (local CA) and Mailpit. The bootstrap administrator is single-use, so its new password and TOTP key are kept in `secrets/e2e-admin.json`. A revoked token may work for up to 10 s (token check cache), so tests wait for that window. |

## Known limitations (accepted)

- No backups (Löschkonzept, Tech Stack). To be listed in the documentation of non-secure parts.
- One replica per service and one node: no high availability.
- A "Sonstiges" booking has no doctor and is not covered by the overlap constraint until reception assigns a doctor (`docs/data-model.md`).
- A stolen access token stays valid until logout, password change or its 15 min expiry (decision 12). There is no way to detect the theft itself.
- Not covered by tests yet: the final hard delete after the retention period (needs the purge job, Phase 5) and booking reminder mails (no reminder job). Nothing has been run on a real Ubuntu host. There is no CI pipeline yet (postponed).
