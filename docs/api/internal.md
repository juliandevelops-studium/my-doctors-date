# Internal contracts

Covers the user JWT, the JWKS endpoint, service tokens, the `database_middleware` operations and the mail templates. Decisions behind it: `docs/decisions.md` (1, 10 to 14, 16).

## 1. User JWT (issued by `user_service`)

| Item | Value |
|-|-|
| Algorithm | EdDSA (Ed25519). Services reject every other `alg`, including `none`. |
| Header | `alg`, `typ=JWT`, `kid` |
| Lifetime | 15 minutes (`exp - iat`), no refresh token |
| Transport | `Authorization: Bearer <jwt>` from `frontend_provider` to the backend. In the browser: HttpOnly, Secure, SameSite=Strict cookie, never readable by JavaScript. |

Claims:

| Claim | Type | Meaning |
|-|-|-|
| `iss` | string | Always `user_service` |
| `aud` | string | Always `praxis-api` |
| `sub` | uuid | User id. The only source of the caller's identity. |
| `roles` | string[] | Subset of `patient, doctor, desk, organisator, systemadmin`. "Nutzer" is implicit. |
| `iat`, `exp` | int | Issue and expiry time (seconds) |
| `jti` | uuid | Token id, used for revocation |
| `mfa` | bool | `true` if a TOTP or recovery code was verified for this login |
| `scope` | string | `full` or `setup`. `setup` is issued while MFA is not confirmed or `must_change_password` is set (UF-03, decision 11). |

Validation in every backend service (middleware or shared package):

1. Signature with the key from JWKS (`kid`), `alg` = EdDSA, `iss`, `aud`, `exp`, `iat` (clock skew max 30 s).
2. `scope` must be `full` unless the route is marked `scope: setup` in `authz.yaml`. `mfa` must be `true` for `scope=full`.
3. `tokenCheck(jti, sub, iat)` on `database_middleware`: the token is not revoked, `iat >= users.sessions_valid_after`, the account is `active`. The result may be cached for at most 10 seconds. Revocations take effect at the next full second, and `user_service` stamps new tokens of that account with `iat = max(now, sessions_valid_after)` (decision 20).
4. Role check against `authz.yaml` (deny by default).

The MFA challenge between password and TOTP step (`POST /auth/login`) is a separate token: `aud=user_service:mfa`, lifetime 5 minutes, one use, claims `sub`, `jti`, `iat`, `exp`. It is not accepted anywhere else.

## 2. JWKS

- `GET /v1/jwks` on `user_service` returns `{ "keys": [ { "kty": "OKP", "crv": "Ed25519", "kid": "...", "x": "..." } ] }`.
- Reachable only inside the cluster (NetworkPolicy), not routed by Traefik. It carries only public keys.
- Services fetch it at start and refresh on an unknown `kid` (rate-limited to once per minute). Two keys can be active during a key rotation.
- The private key is a Kubernetes Secret mounted only into `user_service`.

## 3. Service tokens

Every call between backend services carries `Authorization: Bearer <service token>`.

| Claim | Value |
|-|-|
| `iss` | Caller: `user_service`, `calendar_service`, `purge_job`, `frontend_provider` is **not** a caller of internal services |
| `aud` | Callee: `database_middleware` or `mail_service` |
| `iat`, `exp` | `exp - iat <= 60` seconds |
| `jti` | uuid, logged |
| `act` | (optional) `sub` of the end user on whose behalf the call is made. For audit only, never used for authorisation in the callee. |

- EdDSA. Each caller has its own Ed25519 key pair generated by `make`. The private key is a Secret mounted only into that service. The public keys are in the ConfigMap `service-keys`, mounted into the callees.
- The callee checks signature, `aud`, `exp` and then the **allow list** of its operations (section 4). An operation not allowed for `iss` gives `403`.
- NetworkPolicy is the second layer (SR.02): only the edges of the architecture diagram are open.
- Not used for calls from `frontend_provider` to `user_service` and `calendar_service`. These carry the user JWT.

## 4. `database_middleware` operations

- Every operation is a fixed, parametrised `POST /v1/ops/<name>` with a typed JSON body. There is no endpoint that takes SQL, a table name or a column name (SR.02).
- The allow list is machine-readable in `api/database_middleware.yaml` as `x-allowed-callers` on each operation. `scripts/contractcheck` verifies:
  - `calendar_service` has no operation that returns `password_hash`, MFA data or e-mail tokens.
  - `user_service` has no operation that reads bookings, except `accountDelete`, which cancels and anonymises them.
  - `mail_service` has no operation.
  - Only `purge_job` can call `purgeExpired` and `bookingsCompletePast`.
  - Every operation has at least one caller.
- Booking operations always apply `deleted_at IS NULL`. Ownership filters (`owner_patient_id`, `owner_doctor_id`) are parameters of the operation, so the database applies the ownership rule (SR.03).
- Mapping of database errors: `23P01` (overlap) -> `409 slot_taken`, `23505` (unique) -> `409`, `23514` (check) -> `422`, no row -> `404`.
- Every state-changing operation takes an optional `act` from the service token for the audit trail. Audit rows never contain appointment contents.

Operation groups:

| Group | Operations | Callers |
|-|-|-|
| Accounts | `userCreate`, `userGetByEmail`, `userGetById`, `userList`, `userUpdateProfile`, `userSetPassword`, `userSetEmailVerified`, `userChangeEmail`, `userSetRoles`, `userRecordLoginFailure`, `userRecordLoginSuccess`, `userUnlock`, `userRevokeSessions`, `accountDelete` | `user_service` |
| Tokens and MFA | `tokenCheck` (`user_service`, `calendar_service`), `tokenRevoke`, `emailTokenCreate`, `emailTokenConsume`, `mfaSecretUpsert`, `mfaSecretGet`, `mfaSecretConfirm`, `mfaUseStep`, `mfaDelete`, `recoveryCodesReplace`, `recoveryCodeConsume` | `user_service` |
| Practice | `specialtyList`, `specialtyCreate`, `specialtyDelete`, `serviceList`, `serviceCreate`, `serviceUpdate`, `serviceDelete`, `serviceImport`, `doctorList`, `doctorGetSchedule`, `doctorSetSchedule`, `patientList`, `patientSetMainDoctor` | `calendar_service` |
| Bookings | `calendarGetWindows`, `bookingCreate`, `bookingList`, `bookingGet`, `bookingUpdate`, `bookingCancel`, `bookingAssignDoctor` | `calendar_service` |
| Config and audit | `retentionGet` (`user_service`, `purge_job`), `retentionSet`, `auditWrite` (`user_service`, `calendar_service`, `purge_job`), `auditList` | `user_service` (list, set) |
| Purge job | `purgeExpired(category)`, `bookingsCompletePast` | `purge_job` only |

`purgeExpired` categories: `bookings_cancelled` (A), `bookings_completed_content` (B), `bookings_completed` (C), `users` (D), `audit_log` (E), `tokens`, `email_tokens`. Each call writes one audit row (`action`, `data_category`, `affected_count`).

## 5. `mail_service` templates

`POST /v1/mails` takes `template`, `to` (one address), `locale` (`de`) and typed `params`. Free-text bodies do not exist (decision 14). Callers and templates:

| Template | Caller | Params | UF |
|-|-|-|-|
| `verify_email` | `user_service` | `first_name`, `link` | UF-01 |
| `password_reset` | `user_service` | `first_name`, `link` | UF-10, UF-12 |
| `email_change_confirm` | `user_service` | `first_name`, `link` | profile |
| `email_change_notice` | `user_service` | `first_name` | profile (sent to the old address) |
| `login_warning` | `user_service` | `first_name`, `time` | UF-02 |
| `account_deleted` | `user_service` | `first_name` | UF-13 |
| `booking_confirmed` | `calendar_service` | `first_name`, `service`, `starts_at`, `doctor_name` | UF-05, UF-06 |
| `booking_changed` | `calendar_service` | `first_name`, `service`, `starts_at`, `doctor_name` | UF-06, UF-08 |
| `booking_cancelled` | `calendar_service` | `first_name`, `service`, `starts_at` | UF-07, UF-08 |
| `booking_reminder` | `calendar_service` | `first_name`, `service`, `starts_at` | Erinnerung |

- The mail never contains the booking reason or infos (data minimisation).
- `link` is built by the calling service from the public base URL and a one-time token. `mail_service` only inserts it into the template, and it refuses (`422`) every link that does not start with `PUBLIC_BASE_URL + "/"`.
- Parameters are exact: a missing, an unknown or an extra parameter (for example `link` in a booking mail) gives `422`. Text parameters are single-line without control characters.
- A caller that sends a template of the other service gets `403 template_not_allowed`. Token problems give `401`, a genuine service token of a service that is not a caller gives `403 forbidden`.
- Rate limits: 10 mails per minute and recipient, 300 per minute and calling service (`429`). A compromised service cannot flood one mailbox.
- A failed send returns `502 smtp_failed` without connection details. The calling service logs it and does not retry with changed content.
- Header injection: `to` is validated as a single plain address (no display name, no list, no control characters); the subject comes only from the template.
- Delivery: UTF-8 plain text (quoted-printable), `Auto-Submitted: auto-generated`. `SMTP_TLS=starttls` (default) or `tls` verify the server certificate; credentials are only sent over TLS; `none` exists for a local Mailpit only and logs a warning.
